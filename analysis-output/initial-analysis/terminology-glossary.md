# TiDB Terminology Glossary

**Analysis Commit**: `bd6aa865308ed409fd7010af83a84249bf398d8c`

This glossary defines TiDB-specific terms, architecture concepts, and technical jargon used throughout the codebase.

---

## Core Components

### TiDB
The **SQL layer** of the TiDB distributed database system. This repository contains the code for:
- MySQL protocol server
- SQL parser
- Query planner and optimizer
- Query executor
- Session and transaction management

**Key Point**: TiDB is stateless and can be horizontally scaled.

---

### TiKV
**Distributed row-based storage engine** (separate repository: `tikv/tikv`)
- Key-value store built on RocksDB
- Raft-based replication for high availability
- Multi-version concurrency control (MVCC)
- Coprocessor for push-down computation

**Interface**: Accessed via `tikv/client-go` library

---

### TiFlash
**Distributed columnar storage engine** (separate repository: `pingcap/tiflash`)
- Real-time analytics engine
- Raft Learner replication from TiKV
- Columnar format optimized for OLAP queries
- MPP (Massively Parallel Processing) support

**Use Case**: HTAP workloads (Hybrid Transactional/Analytical Processing)

---

### PD (Placement Driver)
**Cluster metadata and coordination service** (separate repository: `tikv/pd`)

**Responsibilities**:
1. **TSO** (Timestamp Oracle) - Global timestamp allocation
2. **Region routing** - Mapping keys to TiKV nodes
3. **Load balancing** - Region scheduling and rebalancing
4. **Metadata management** - Cluster topology

**Interface**: Accessed via `tikv/pd/client`

---

## Architecture Concepts

### Region
**Fundamental unit of data distribution** in TiKV

- Size: ~96MB of data (default)
- Replication: 3 replicas (default, via Raft)
- Leader election: Raft-based
- Splitting: Automatic when size exceeds threshold

**Example**:
```
Key Range: [a, z)
Region 1: [a, m)  → TiKV-1 (Leader), TiKV-2 (Follower), TiKV-3 (Follower)
Region 2: [m, z)  → TiKV-2 (Leader), TiKV-3 (Follower), TiKV-1 (Follower)
```

---

### InfoSchema
**In-memory metadata cache** containing table/column definitions

- **Location**: `pkg/infoschema/`
- **Content**: Table schemas, index definitions, partition info
- **Versioning**: Schema version increments on DDL operations
- **Reload**: Triggered by domain on schema changes

**Usage**: Planner and executor query InfoSchema for table metadata

---

### Domain
**Global lifecycle manager** for a TiDB instance

- **Singleton**: One per TiDB server process
- **Responsibilities**:
  - InfoSchema management
  - DDL executor coordination
  - Statistics handle
  - Background workers (auto-analyze, TTL)
  - Privilege manager

**Location**: `pkg/domain/domain.go`

---

### Session
**Execution context** for a client connection

- **State**: Variables, transaction, prepared statements
- **Lifecycle**: Created on connection, destroyed on disconnect
- **Thread-safety**: Each session is single-threaded

**Location**: `pkg/session/session.go`

---

### Transaction
**ACID unit of work** with snapshot isolation

**Modes**:
1. **Optimistic**: Conflict detection at commit time
   - Faster for low-contention workloads
   - Retries on conflict

2. **Pessimistic**: Lock acquisition on write
   - Prevents conflicts proactively
   - Better for high-contention workloads

**Phases**:
```
Idle → Active (first write) → Preparing → Committing → Committed/Aborted
```

---

## Query Processing Terms

### AST (Abstract Syntax Tree)
**Parsed representation of SQL**

- Generated by `pkg/parser/`
- Node types defined in `pkg/parser/ast/`
- Example nodes: `SelectStmt`, `TableName`, `BinaryOperationExpr`

---

### Logical Plan
**Abstract query plan** representing query semantics

- **Operators**: `LogicalSelection`, `LogicalJoin`, `LogicalAggregation`
- **Properties**: No physical implementation details
- **Optimization**: Target of rule-based optimizations

**Example**:
```
LogicalAggregation (GROUP BY)
    ↓
LogicalSelection (WHERE)
    ↓
LogicalJoin
    ├── LogicalDataSource (table t1)
    └── LogicalDataSource (table t2)
```

---

### Physical Plan
**Executable query plan** with implementation details

- **Operators**: `HashJoin`, `IndexScan`, `TableScan`, `HashAgg`
- **Properties**: Execution order, access methods, join algorithms
- **Selection**: Based on cost model

**Example**:
```
HashAggExec
    ↓
SelectionExec
    ↓
HashJoinExec
    ├── TableReaderExec (t1)
    └── IndexReaderExec (t2)
```

---

### Executor
**Component that executes a physical plan operator**

- **Interface**: `Open()`, `Next()`, `Close()`
- **Pattern**: Iterator (Volcano) model with chunking
- **Data Flow**: Pull-based (parent calls child's `Next()`)

**Chunk Batching**: Processes ~1024 rows per `Next()` call

---

### Chunk
**Columnar data batch** for efficient execution

- **Structure**: Array of columns (not array of rows)
- **Benefits**: Cache locality, vectorized operations
- **Size**: Typically 1024 rows (configurable)

**Location**: `pkg/util/chunk/`

---

### Coprocessor (Cop)
**Push-down computation engine** in TiKV

**Supported Operations**:
- `Selection` (filters)
- `TableScan`/`IndexScan`
- `Aggregation` (`COUNT`, `SUM`, etc.)
- `TopN` (sorting + limit)

**Benefits**: Reduces network transfer, parallelizes computation

**Request Type**: `CopRequest` sent via `pkg/distsql/`

---

### MPP (Massively Parallel Processing)
**Distributed query execution** on TiFlash

**Use Case**: Complex analytical queries (joins, aggregations)
**Execution**: Task fragments distributed across TiFlash nodes
**Coordination**: TiDB orchestrates MPP tasks

**Example Query**:
```sql
SELECT region, SUM(sales)
FROM orders
WHERE year = 2024
GROUP BY region
```
→ Aggregation pushed to TiFlash MPP

---

## Transaction & Concurrency Terms

### TSO (Timestamp Oracle)
**Globally unique, monotonically increasing timestamp** from PD

**Usage**:
- Transaction start timestamp (`start_ts`)
- Transaction commit timestamp (`commit_ts`)
- Snapshot read timestamp

**Allocation**: From PD via gRPC

**Format**: 64-bit integer (physical time + logical counter)

---

### MVCC (Multi-Version Concurrency Control)
**Concurrency control mechanism** in TiKV

**Concept**: Multiple versions of same key coexist
**Versioning**: Each write creates new version with timestamp
**Reads**: See snapshot at specific `start_ts`
**Garbage Collection**: Old versions cleaned by GC

**Benefits**: Lock-free reads, snapshot isolation

---

### 2PC (Two-Phase Commit)
**Distributed transaction commit protocol**

**Phases**:
1. **Prewrite**: Lock primary key and all secondary keys
2. **Commit**: Write commit record for primary, clean up secondaries

**Implementation**: Percolator-based algorithm

**Commit Record**:
```
Key: {Primary Key}
Value: {commit_ts}
```

---

### Lock
**Pessimistic lock** for write-write conflict prevention

**Types**:
- **Primary Lock**: First key locked in transaction
- **Secondary Locks**: Other keys in transaction

**TTL** (Time-To-Live): Lock expires if transaction exceeds TTL

**Resolution**: Stale locks automatically resolved by readers

---

### Write Conflict
**Concurrent modification** of same key

**Detection**: At commit time (optimistic) or write time (pessimistic)

**Resolution**:
- Optimistic: Transaction aborts, client retries
- Pessimistic: Blocked until lock released

**Error Code**: `ErrWriteConflict`

---

## DDL Terms

### Online DDL
**Schema changes without blocking** read/write operations

**Approach**: Incremental state transitions with schema versioning

**States** (for column add):
```
None → Delete Only → Write Only → Write Reorg → Public
```

**Synchronization**: Schema lease mechanism (~45s)

---

### Owner
**Single TiDB instance** responsible for DDL execution

**Election**: Via etcd lease
**Responsibility**: Only owner executes DDL jobs
**Job Queue**: Persisted in TiKV, consumed by owner

---

### Schema Version
**Incrementing counter** for schema changes

**Usage**: All TiDB instances must use schema within 2 versions of latest
**Reload**: Domain reloads InfoSchema when version updates

---

### Reorg Worker
**Background worker** for data reorganization during DDL

**Use Cases**:
- Index backfilling
- Column type changes
- Table restructuring

**Concurrency**: Configurable worker count

---

## Optimization Terms

### Predicate Push-Down
**Move filters closer to data source** to reduce data transfer

**Example**:
```sql
SELECT * FROM t WHERE id > 100
```
→ Filter `id > 100` pushed to TiKV coprocessor

---

### Index Selection
**Choose optimal index** for table access

**Factors**:
- Cardinality (selectivity)
- Index column order
- Covering index (avoids table lookup)

**Algorithm**: Cost-based comparison

---

### Join Reordering
**Optimize join order** to minimize intermediate results

**Algorithm**: Dynamic Programming (for <7 tables) or Greedy (for ≥7 tables)

**Cost Model**: Based on table statistics (row count, NDV)

---

### Plan Cache
**Reuse execution plans** for repeated queries

**Types**:
1. **Prepared Statement Cache**: Per-session cache
2. **Non-Prepared Cache**: Shared cache for similar queries

**Key**: Normalized SQL text or plan digest

**Eviction**: LRU (Least Recently Used)

---

### Statistics
**Table/column metadata** for query optimization

**Components**:
- **Histogram**: Value distribution
- **Count-Min Sketch**: Cardinality estimation
- **TopN**: Most frequent values
- **NDV**: Number of Distinct Values

**Collection**:
- Manual: `ANALYZE TABLE t`
- Automatic: Background worker (configurable)

**Storage**: Persisted in system tables (`mysql.stats_*`)

---

## Storage Terms

### Key-Value (KV)
**Fundamental storage abstraction**

**Encoding**:
```
Table Row:  t{tableID}_r{rowID} → [col1, col2, ...]
Index:      t{tableID}_i{indexID}_{indexValue} → {rowID}
```

**Operations**: Get, Set, Delete, Scan

---

### Snapshot
**Consistent read view** at specific timestamp

**Properties**:
- Read-only
- Isolation from concurrent writes
- Automatic GC after transaction

**Usage**: All reads within transaction use same snapshot

---

### MemBuffer
**Write buffer** for pending transaction changes

**Staging**: Supports nested transactions (savepoints)
**Flush**: Committed to TiKV on transaction commit

---

### Range
**Contiguous key interval** for scans

**Format**: `[StartKey, EndKey)`

**Example**:
```
Index scan: WHERE id BETWEEN 10 AND 100
→ Range: [t1_i1_10, t1_i1_100]
```

---

## Observability Terms

### Slow Query Log
**Dedicated log file** for queries exceeding threshold

**Threshold**: Configurable (default 300ms)

**Fields**: 60+ fields including:
- Query time, memory, disk usage
- Plan digest, execution details
- Row counts (scanned vs. returned)

---

### Plan Digest
**Hash of execution plan** for query grouping

**Usage**: Group similar queries in monitoring
**Format**: SHA-256 hex string

---

### Statement Summary
**Aggregated query statistics** (similar to `performance_schema` in MySQL)

**Metrics**:
- Execution count, total latency
- Min/max/avg latency
- Rows examined/returned

**Tables**: `information_schema.statements_summary`

---

### Top SQL
**Real-time top queries** tracking system

**Features**:
- CPU usage per SQL
- Sampling-based (low overhead)
- Integration with monitoring dashboards

---

### Flight Recorder
**Circular buffer** for post-mortem analysis

**Content**: Trace events from recent operations
**Capacity**: 1024 events (default)
**Trigger**: Slow queries, failures, manual dump

---

## Configuration Terms

### System Variable
**Configuration parameter** affecting SQL behavior

**Scopes**:
- **Global**: Cluster-wide setting
- **Session**: Per-connection setting

**Examples**:
```sql
SET GLOBAL tidb_enable_vectorized_expression = ON;
SET SESSION tidb_hash_join_concurrency = 8;
```

---

### Instance Config
**TOML file configuration** for TiDB server

**Location**: `tidb.toml`

**Sections**:
- `[server]`: Network settings
- `[log]`: Logging configuration
- `[performance]`: Performance tuning
- `[security]`: TLS and authentication

---

### Schema Lease
**Time window** for schema synchronization across TiDB instances

**Default**: 45 seconds
**Purpose**: Ensure all instances converge on schema version
**Critical**: Must be longer than 2x clock skew

---

## Testing Terms

### TestKit
**SQL testing utility** in `pkg/testkit/`

**Usage**:
```go
tk := testkit.NewTestKit(t, store)
tk.MustExec("use test")
tk.MustQuery("select * from t").Check(testkit.Rows("1", "2"))
```

**Features**: Automatic store creation, result assertion

---

### MockStore
**In-memory TiKV implementation** for testing

**Implementation**: UniStore (embedded KV based on Pebble)
**Benefits**: Fast tests without external dependencies

---

### Failpoint
**Fault injection** framework

**Usage**:
```go
failpoint.Inject("SlowQuery", func() {
    time.Sleep(time.Second)
})
```

**Activation**: Via environment variable or API call

---

## Advanced Concepts

### HTAP (Hybrid Transactional/Analytical Processing)
**Single database** supporting both OLTP and OLAP workloads

**Implementation**:
- OLTP: TiKV (row-based)
- OLAP: TiFlash (columnar)
- Replication: Real-time via Raft Learner

---

### Common Handle
**User-defined primary key** used as row handle

**Alternative**: Auto-generated `_tidb_rowid`

**Benefits**: Avoids extra table lookup for primary key access

---

### Clustered Index
**Table data physically organized** by primary key

**Example**:
```sql
CREATE TABLE t (
    id INT,
    name VARCHAR(50),
    PRIMARY KEY (id) CLUSTERED
);
```
→ Rows stored in primary key order

---

### Partition Pruning
**Skip irrelevant partitions** during query execution

**Example**:
```sql
SELECT * FROM orders PARTITION (p2024)
WHERE order_date = '2024-06-15'
```
→ Only access `p2024` partition

---

### Global Index
**Index across all partitions** (experimental feature)

**Alternative**: Local indexes (per-partition)

---

### TTL (Time-To-Live)
**Automatic data expiration** and cleanup

**Configuration**:
```sql
CREATE TABLE logs (
    id INT,
    created_at TIMESTAMP
) TTL = created_at + INTERVAL 30 DAY;
```

**Cleanup**: Background worker deletes expired rows

---

### Resource Control
**Multi-tenancy resource isolation**

**Mechanism**: Resource groups with quotas
**Metrics**: Request Units (RU) for reads/writes
