## Stage 1: Connection and Protocol Handling

### Client Connection

When your MySQL client connects to TiDB:

**File**: [`pkg/server/server.go:344`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/server/server.go#L344)

```go
func (s *Server) Run() error {
    // Start listening on MySQL port (default 4000)
    for {
        conn, err := s.listener.Accept()
        if err != nil {
            continue
        }

        // Create new client connection
        clientConn := s.newConn(conn)

        // Handle in new goroutine (one per connection)
        go clientConn.Run(s.ctx)
    }
}
```

**Key Insight**: One goroutine per client connection. At 10K connections, that's 10K goroutines (cheap in Go).

```go
func (cc *clientConn) handshake(ctx context.Context) error {

    err := cc.writeInitialHandshake()
```

## Stage 3: Logical Plan Building

**File**: [`pkg/planner/core/logical_plan_builder.go:1200`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/planner/core/logical_plan_builder.go#L1200)

```go
func (b *PlanBuilder) buildSelect(ctx context.Context, sel *ast.SelectStmt) (Plan, error) {
    // 1. Build FROM clause
    p, err := b.buildDataSource(ctx, sel.From)

    // 2. Build WHERE clause
    if sel.Where != nil {
        p, err = b.buildSelection(ctx, p, sel.Where)
    }

    // 3. Build SELECT fields (projection)
    p, err = b.buildProjection(ctx, p, sel.Fields)

    return p, nil
}
```

**Logical Plan for Our Query**:

```
LogicalProjection (select name, email)
    ↓
LogicalSelection (where id = 42)
    ↓
LogicalDataSource (table users)
```

**Why "Logical"?**: No execution details yet - just semantics.

### Schema Information

The planner needs table metadata:

**File**: [`pkg/planner/core/logical_plan_builder.go:2800`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/planner/core/logical_plan_builder.go#L2800)

```go
func (b *PlanBuilder) buildDataSource(ctx context.Context, tn *ast.TableName) (LogicalPlan, error) {
    // Get InfoSchema (metadata cache)
    is := b.ctx.GetInfoSchema().(infoschema.InfoSchema)

    // Look up table definition
    tbl, err := is.TableByName(tn.Schema, tn.Name)

    // Get indexes
    indices := tbl.Indices()

    // Create data source node
    ds := LogicalDataSource{
        TableName: tn,
        Table:     tbl,
        Columns:   tbl.Cols(),
        Indices:   indices,
    }

    return &ds, nil
}
```

**InfoSchema Contains**:
- Table definitions (columns, types)
- Index definitions
- Partition information
- Foreign keys, constraints

## Stage 4: Optimization

```go
func Optimize(ctx context.Context, sctx sessionctx.Context, node ast.Node) (Plan, error) {
    // 1. Build logical plan
    logic, err := planBuilder.build(ctx, node)

    // 2. Apply optimization rules
    logic, err = logicalOptimize(ctx, logic, sctx)

    // 3. Generate physical plans

    return physical, nil
}
```

```go

    &projectionEliminator{},      // Remove redundant projections

    &ppdSolver{},                 // Predicate push down
```

**For Our Query**:

1. **Column Pruning**: Only fetch `id`, `name`, `email` (not all columns)
2. **Predicate Push Down**: Apply `WHERE id = 42` at storage layer
3. **Index Selection** (if `id` is primary key): Use index access instead of table scan

**After Optimization**:

```
LogicalProjection (name, email)
    ↓
LogicalSelection (id = 42) ← Can be pushed to storage!
    ↓
LogicalDataSource (users, index: PRIMARY)
```

### Physical Plan Generation

**File**: [`pkg/planner/core/exhaust_physical_plans.go`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/planner/core/exhaust_physical_plans.go)

For each logical operator, generate possible physical implementations:

```go
func (ds *LogicalDataSource) exhaustPhysicalPlans() []PhysicalPlan {
    plans := make([]PhysicalPlan, 0, len(ds.possibleAccessPaths))

    // Option 1: Table scan
    tableScan := PhysicalTableScan{...}
    plans = append(plans, tableScan)

    // Option 2: Index scan (for each index)
    for _, idx := range ds.possibleAccessPaths {
        indexScan := PhysicalIndexScan{Index: idx}
        plans = append(plans, indexScan)
    }

    return plans
}
```

**Cost-Based Selection**:

```go
// Calculate cost for each plan
for _, plan := range plans {
    cost := calculateCost(plan, statistics)
    if cost < bestCost {
        bestPlan = plan
        bestCost = cost
    }
}
```

**Cost Factors**:
- Row count (from statistics)
- I/O cost (table scan vs. index scan)
- CPU cost (filtering, sorting)
- Network cost (distributed execution)

**Final Physical Plan** (assuming `id` is primary key):

```
PhysicalProjection (name, email)
    ↓
PointGetExecutor (id = 42, index: PRIMARY)
```

**Optimization**: Point get is fastest path - single key lookup!

## Stage 6: Execution

### Open Phase

**File**: [`pkg/executor/point_get.go:100`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/executor/point_get.go#L100)

```go
func (e *PointGetExecutor) Open(ctx context.Context) error {
    // Get transaction snapshot
    txnCtx := e.ctx.GetSessionVars().TxnCtx
    e.snapshot = e.ctx.GetStore().GetSnapshot(txnCtx.StartTS)

    return nil
}
```

**What Happens**:
1. Get snapshot timestamp from PD (if not already in transaction)
2. Create read snapshot at that timestamp
3. Snapshot provides consistent view (MVCC)

### Next Phase (Data Fetching)

**File**: [`pkg/executor/point_get.go:150`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/executor/point_get.go#L150)

```go
func (e *PointGetExecutor) Next(ctx context.Context, req *chunk.Chunk) error {
    // Build key for row lookup
    // Format: t{tableID}_r{rowID}
    key := tablecodec.EncodeRowKey(e.tblInfo.ID, e.handle)

    // Get from TiKV snapshot
    value, err := e.snapshot.Get(ctx, key)
    if err != nil {
        return err
    }

    // Decode row data
    row, err := tablecodec.DecodeRow(value, e.tblInfo.Columns)

    // Append to result chunk
    req.AppendRow(row)

    e.finished = true
    return nil
}
```

**Key Encoding Example**:
```
Table ID: 100
Row ID: 42
Key: t100_r42

TiKV stores: t100_r42 → [42, "Alice", "alice@example.com", ...]
```

### Communication with TiKV

**File**: [`pkg/store/driver/tikv_driver.go`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/store/driver/tikv_driver.go)

```go
// snapshot.Get() internally:
func (s *tikvSnapshot) Get(ctx context.Context, key []byte) ([]byte, error) {
    // 1. Find region for this key (from PD cache)
    region := s.regionCache.LocateKey(key)

    // 2. Send RPC to TiKV leader for that region
    req := &kvrpcpb.GetRequest{
        Context: &kvrpcpb.Context{RegionId: region.ID},
        Key:     key,
        Version: s.version, // Snapshot timestamp
    }

    resp, err := s.client.SendRequest(ctx, region.Leader, req)

    return resp.Value, nil
}
```

**Network Flow**:
```
TiDB → PD: Where is key "t100_r42"?
PD → TiDB: Region 500 on TiKV-3

TiDB → TiKV-3: Get "t100_r42" at timestamp 12345
TiKV-3 → TiDB: Value: [42, "Alice", "alice@example.com", ...]
```

```go
type Chunk struct {
    columns     []*Column  // Columnar storage

type Column struct {
```

**Why Columnar?**
- Cache-friendly access
- SIMD vectorization possible
- Efficient for filtering

### Projection Execution

**File**: [`pkg/executor/projection.go:180`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/executor/projection.go#L180)

```go
func (e *ProjectionExec) Next(ctx context.Context, req *chunk.Chunk) error {
    // Get chunk from child (PointGetExecutor)
    inputChunk := chunk.NewChunkWithCapacity(e.childSchema, e.maxChunkSize)
    err := e.children[0].Next(ctx, inputChunk)

    // Project columns (select name, email)
    for rowIdx := 0; rowIdx < inputChunk.NumRows(); rowIdx++ {
        row := inputChunk.GetRow(rowIdx)
        projectedRow := e.evaluateProjection(row)  // Extract name, email
        req.AppendRow(projectedRow)
    }

    return nil
}
```

## Stage 8: Result Serialization

### MySQL Protocol Encoding

**File**: [`pkg/server/conn.go:1800`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/server/conn.go#L1800)

```go
func (cc *clientConn) writeResultset(ctx context.Context, rs ResultSet) error {
    // 1. Send column definitions
    err := cc.writeColumnInfo(rs.Columns())

    // 2. Send rows
    for {
        chunk, err := rs.Next(ctx)
        if chunk.NumRows() == 0 {
            break
        }

        for rowIdx := 0; rowIdx < chunk.NumRows(); rowIdx++ {
            row := chunk.GetRow(rowIdx)
            cc.writeRow(row)
        }
    }

    // 3. Send EOF packet
    return cc.writeEOF()
}
```

**Wire Protocol**:
```
Column Definition Packet (name: VARCHAR(255))
Column Definition Packet (email: VARCHAR(255))
EOF Packet
Row Data Packet: ["Alice", "alice@example.com"]
EOF Packet
```

## Distributed Query Example

For a more complex query:

```sql
SELECT region, COUNT(*), AVG(amount)
FROM orders
WHERE created_at > '2024-01-01'
GROUP BY region;
```

### Execution Plan

```
HashAggExec (final aggregation)
    ↓
TableReaderExec (distributed scan)
    ↓
[DistSQL Coprocessor on multiple TiKV nodes]
    ↓ (parallel execution)
Partial Aggregation + Filter on TiKV
```

### Coprocessor Push-Down

**File**: [`pkg/distsql/distsql.go:57`](https://github.com/pingcap/tidb/blob/bd6aa865/pkg/distsql/distsql.go#L57)

```go
func Select(ctx context.Context, sctx sessionctx.Context, kvReq *kv.Request) (SelectResult, error) {
    // 1. Build coprocessor request
    copReq := buildCopRequest(kvReq)

    // 2. Send to all regions covering key range
    regions := getRegionsForRange(copReq.KeyRanges)

    // 3. Send requests in parallel
    for _, region := range regions {
        go sendCopRequest(region, copReq)
    }

    // 4. Stream results back
    return newSelectResult(responses), nil
}
```

**What Gets Pushed Down**:
- Filter: `WHERE created_at > '2024-01-01'`
- Partial aggregation: `COUNT(*)`, `SUM(amount)`, `COUNT(amount)`
- GroupBy: `region`

**Benefits**:
- 1000 TiKV nodes → 1000x parallelism
- Only aggregated results returned (not all rows)
- Network traffic reduced by 100-1000x

## Key Takeaways

1. **Layered Design**: Each stage has clear responsibility
   - Protocol → Parser → Planner → Optimizer → Executor → Storage

2. **MySQL Compatibility**: Full MySQL protocol implementation
   - Drop-in replacement for MySQL clients

3. **Plan Caching**: Repeated queries skip parsing + optimization
   - 10x faster for cached plans

4. **Push-Down Computation**: Critical for distributed performance
   - Filters, aggregations, projections executed at storage layer

5. **Chunk-Based Execution**: Memory-efficient batching
   - Columnar layout for cache efficiency

6. **Snapshot Isolation**: Consistent reads via MVCC
   - Timestamp from PD ensures cluster-wide consistency
